Post-purchase comms · flow design

Adding a release

Today you type a release title that must secretly match the Shopify product exactly, then go and find the importer. This turns it round: drop the export first, and the app shows what is in the file and asks you to tick which products are this release. The string nobody types is the string that has to be right.

The case for changing it

Four faults, each measured against the code

Not opinions. Every one of these was run against the tree before it was written down, and one of them is a live routing bug that would put a framed print on the unframed timeline.

A wrong title fails silently, and blames the file

The release title must equal the Shopify product title, or start it and be followed by “ - ”. That rule lives in a ? tooltip. Get it wrong and the import succeeds with nothing in it, and the summary calls your orders somebody else’s products.

filterItemsForRelease(items, ['Faling Light']) → matched 0 · filteredOut 296 summary reads: New orders 0 · Other products 296

A hyphenated variant sends a framed print down the unframed timeline

The batch is chosen from the variant, which is whatever follows the last “ - ”. A frame finish in the title takes that slot, so the word “framed” is never seen. No framing email, and a promise date set on the wrong flow.

splitLineItemTitle('Falling Light - Framed - Oak') → { title: 'Falling Light - Framed', variant: 'Oak' } classifyFulfilment('Oak') → unframed ✗ classifyFulfilment('Falling Light - Framed - Oak') → framed ✓

An empty file is reported as a partial success

The whole-file faults go down the same channel as a bad row, so a file with nothing in it draws a count of one and a reassurance that is false in exactly the case where reassurance does damage.

parseShopifyOrderExport('') → issues: [{ row: 0, reason: 'File is empty' }] drawn as: “1 row could not be read” “Everything else was imported.”

Nothing stops two people creating the same release twice

There is no uniqueness check anywhere, and dedupe is scoped per release. Two operators dropping the same export a minute apart get two releases, 588 orders, and every collector on two full milestone sequences.

createRelease() validates: title non-empty, artist non-empty dedupe: orders.filter(o => o.releaseId === releaseId) ^ per release only

The kit’s box wraps a native file input with accept=".csv", and browsers silently swallow a non-matching drop — drop the .xlsx you actually have and nothing happens at all. Step one, rejected

A file that is not an order export gets a whole-file answer

Never a row count. Five diagnoses, each said only where it is true — including the one that bites hardest today: a genuine Shopify export opened and re-saved in Excel under a European locale comes back semicolon-delimited and is currently told it is not an export at all.

●
This file is semicolon-separated
Re-export from Shopify, or save it as CSV (comma-delimited).
●
That is not a Shopify order export
No Name or Lineitem name column. Columns found: Order Number, Print Name, Fulfilment…
●
That file is empty
Nothing was read, and nothing was created.
●
No row in this file could be read
296 rows, every one missing a readable “Created at” date.

The last one is new: a bad date format currently produces one issue per row — 296 copies of the same sentence in one dialogue — and nothing blocks, so the orders are written with no order date at all.

The counts are two different quantities and the flow says both: an order in this app is one row per print, so 294 records come from 293 Shopify orders — #AA10418 bought a framed and an unframed. Guessing which number a reader meant is the fault this screen exists to end.

What the file decides

  • Which products, and therefore the Shopify join key — stored as the exact line-item strings.
  • Which batches exist. A print with only unframed orders gets one batch and no batch language anywhere.
  • Print or sculpture, proposed as sculpture unless a row says framed — a bronze sold in finishes would otherwise take the printing-and-framing sequence.
  • The title, suggested and editable. It is a display name now, not a key.

What it cannot, so it asks

  • Artist. Not in a Shopify order export in any column.
  • Edition size, and it is never prefilled from the order count: in all four real exports the orders exceed the stated edition, so “294 on an edition of 150” is normal and must not be validated as an error.
  • Which milestone emails this release sends.
Step two, refused

What shuts the button, and what it says

A shut control says why — the house rule. These are the four that stop a write, and each one names the thing to do instead rather than the rule it broke.

SituationWhat the flow does

A product another release already claims “Falling Light - Framed” is already claimed. Falling Light, created 6 minutes ago by Priya Nair — 294 orders. Add these orders to it instead. [Open Falling Light] carries the same file, already read, straight to its Add-orders step.
Nothing ticked Shut, with Tick at least one product. An empty match now means nothing — today the matcher returns everything when handed an empty list, which is a live landmine the moment a release exists with no confirmed products.
No artist The requirement is in the field’s own note, and the shut button repeats it. A requirement that only appears on hover is a requirement half the people never see.

And one that does not block: everything in the “things to check” table. A duplicate row, a missing email, a collector in two batches, a line belonging to another release — all real, all reported before the write, none of them a reason to stop.

The thing this design owes you

One mis-drop must not be permanent

Today a mis-click at the New release door costs an empty release you can ignore. Under this flow one wrong file costs a release, 294 orders, two batches and a history — and the wrong file is named almost identically to the right one. There is no deleteRelease in the data layer and no way to undo an import.

So the flow ships with the remover, not after it. Each import is recorded as an intake, and every order remembers which intake made it.

Undo the import of falling-light-2026-04-26.csv?×

It hard-deletes, deliberately: a soft-removed order stays in the dedupe set, so “removing” 294 orders would poison the re-import of the correct file. Both this and Delete release are refused the moment any send has fired.

Medium term

The day the Shopify sync lands

The whole point of storing the ticked strings rather than a typed title: on sync day there is one new function and no new screens.

What changes

  • One function beside the CSV parser: fromShopifyApi(json), producing the same line items.
  • It calls the same addOrders the CSV door calls, with the source labelled Shopify instead of a filename.
  • The upload step disappears for a synced release; you land straight on the products list, fed by the API.
  • The sync writes the real product id onto the match it made, and from then the id is the join and the titles are the fallback.

What does not

  • Every screen’s words. The release page never says CSV — it says when orders were last added and how many. Both stay true.
  • The reconciliation. The first synced pass over a CSV-populated release matches rather than creating 294 duplicates.
  • The product match, the guards, the counts, the batch routing, the undo.
  • The importer’s parsing, which the CSV path keeps for as long as anyone exports a file.

And what only the sync can buy, so it is not attempted now: refunds and cancellations (this design reads the payment status, reports it, and never acts on it), fulfilment closing the loop on dispatch, and real order ids for the Shopify links.

Before it gets built

Four calls you might reasonably overrule

1 · The title stops being the Shopify key

This is the one that cannot be retrofitted cheaply — orders imported under title-matching carry no product reference, so on sync day you reconcile or you map four releases and 603 orders by hand. It also makes renaming a release safe.

The cost, stated: it removes the informal collision signal a second operator relied on, which is why the claimed-product guard is not optional. Everything else here is additive; this one is not.

2 · “Set up without a file” stays as a second door

A release can be created before any order exists — useful before a drop, and the sync will do exactly this. The cost is a state that must be drawn and guarded, and someone will create one by habit.

Say the word and the link goes; the empty-match guard stays either way.

3 · Payment status is read, reported, and not acted on

A refunded collector receives every milestone email today, in silence. This reports the status and stops there, one step short of acting — consistent with the v1 rule that cancellations are marked by hand.

Honestly: no fixture carries a refund, so the wording is designed from the column and not from evidence. Worth checking the real vocabulary before it is settled.

4 · Two panes, not one screen

The second pane cannot be drawn until the file is read, and there is no staged-flow vocabulary in the design system to draw a rail with. Position is carried by the dialogue title and a Back verb rather than a stepper.

The alternative is a full page for setup, which is a bigger change than the flow needs.
