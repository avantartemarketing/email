Falling Light · the release page

Three ways to separate the tabs from the batches

The strip runs seven peers. All orders is everything on the release, All emails is everything it sends, and the five after them are one production run each — but nothing in the row says so. Every option below keeps the same seven destinations and changes only what rank they are drawn at. Each is rendered in the real system, at the width the release page actually gets.

Option 1

Two tiers, and two different kinds of control

Three tabs, and picking Batches opens a second row beneath it. The second row is not a smaller tab strip — it is the kit's segmented control, and the system has already ruled the difference: “a segmented toggle is NOT a tab — it changes a value while the screen stays the screen, where a tab changes what is on screen.” That is exactly the relation here. Once you are inside Batches the screen stays the batch screen; you are choosing which run you are looking at.

What it buys

  • The rank is in the shape, not the size. A smaller tab is still a tab; a different control is a different level.
  • Every batch stays one click away and on screen — nothing is hidden behind a menu.
  • The top row is fixed at three whatever a release does to itself.

What it costs

  • A second row, ~34px, on the batch tab only.
  • The segmented control runs out of width around eight batches; beyond that it needs to wrap or scroll.
  • One CSS change: the control right-aligns itself everywhere it is used today.
Option 2

One row; the batch rides inside its own tab

Still three tabs, but the third one carries the batch you are on and opens a list. The strip never gains a row and never gains a member — it says Batches · Framed 2 the way a breadcrumb would, so the answer to “where am I?” is in the same place whatever you clicked.

What it buys

  • One row for ever. Thirty batches cost the same width as two.
  • The open batch is named in the strip, so the page always says where you are without a second surface.
  • The menu is the kit's existing popover — no new vocabulary at all.

What it costs

  • The batch list is hidden until you ask for it: you cannot see that Framed 3 exists without opening the menu.
  • One control doing two jobs — enter the tab, and change the batch.
  • Moving between two batches is two clicks, where the flat strip is one.
Option 3

The batches become a sub-rail inside the tab

Three tabs, and the Batches tab opens onto a split: the runs down the left, the run's own screen to the right. The hierarchy is not signalled — it is physical. Nothing about a list nested inside a pane can be read as a peer of the thing above it.

What it buys

  • The clearest hierarchy of the three, and the only one that does not depend on somebody learning a convention.
  • Scales to any number of batches — the list scrolls in its own column.
  • You can read the whole set while working on one: which runs exist, how big, in what order.

What it costs

  • 196px off a table that is already wide — the orders table inside a batch is fourteen columns.
  • A second vertical navigation on a page that already has the shell's rail six inches to its left.
  • The most work to build, and the one that changes the batch screen's layout rather than only its heading.

Where I would land

Option 1. It is the only one whose hierarchy comes from a distinction the system has already made and written down, which means it will read the same way the next time somebody nests something. It costs one row on one tab, hides nothing, and fixes the top strip at three members permanently.

Take option 2 instead if releases routinely run past eight batches — that is where the segmented control stops fitting and the menu stops being a compromise. Take option 3 only if the batch list becomes something people scan rather than something they pick from; today it is five rows read once.

All three leave All orders and All emails exactly where they are, which is the half of the strip that gets used every day.
